# Publishing the Android application

Everything needed to get ITSaNAS onto a phone without sideloading, and the
parts nobody but Nicolas can do.

---

## 0. The one irreversible decision

**The release key signs every version of this application, for ever.** Google
will not re-key a listing. Lose the key and the listing is dead: the only way
forward is a new application, a new package name, and every tester
uninstalling and starting again — losing their node with it.

So it is generated by Nicolas, held by Nicolas, and backed up the way the
24-word phrase is. It is not in this repository, it never passes through an
agent, and `.gitignore` refuses both the key and the file that names it.

Until such a key exists, `scripts/build-apk.sh` signs with the **debug** key
and says so on every run. A debug-signed build installs on a phone by hand and
is rejected by Play.

---

## 1. Make the key — your command, your machine

Run this once. The JDK this project already uses is at `D:/Android/jdk`.

```
D:/Android/jdk/bin/keytool -genkeypair -v \
  -keystore D:/Android/itsanas-release.jks \
  -alias itsanas \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -dname "CN=ITSaNAS, O=ITSomething, C=FR"
```

It asks for a password twice. **10000 days** is about 27 years: Play requires a
key valid past 2033, and a key that expires mid-life is the same problem as a
lost one.

Then write `android/keystore.properties` — git-ignored, and the build reads it:

```
storeFile=D:/Android/itsanas-release.jks
storePassword=<what you just typed>
keyAlias=itsanas
keyPassword=<the same, unless you set a separate one>
```

Back up **both** files somewhere your house burning down would not reach. Same
rule as the recovery phrase, same reason.

---

## 2. Build what Play accepts

```
bash scripts/build-apk.sh bundle
```

That produces `android/app/build/outputs/bundle/release/app-release.aab`.

A **bundle** is what Google Play takes for a new application. It is not
installable on a phone — for that, `bash scripts/build-apk.sh release` still
produces an APK, which is what to sideload and what to keep using for testing
at home.

The script prints which key it used before it builds. Read that line.

## 3. The account — personal or ITSomething

This is a real decision and it changes the calendar, so it is written down
rather than left to the moment.

| | Personal Google account | Organisation (ITSomething) |
| --- | --- | --- |
| Cost | $25 once | $25 once |
| Verification | identity documents | **D-U-N-S number** for the company, which can take days to obtain |
| Path to closed/open testing | **~12 testers running a closed test for ~14 continuous days** before production access | not subject to the 12-tester rule |
| Publisher shown to users | a personal name | ITSomething |

**Internal testing is available immediately on either**, which is the route
that matters here: up to 100 testers invited by email address, no 14-day wall,
no production review. It is the answer to "I do not want to sideload".

Two cautions. These policies change — treat the table as the shape, not the
letter, and read the console. And the publisher name is shown to everyone who
installs the application, which is a choice about what this project is rather
than a technicality.

## 4. What the console will ask, with the answers this project has

Prepared here so the form is not filled in from memory at eleven at night.

**Data safety.** The application collects nothing and sends nothing to a server
belonging to anybody else. It stores the person's own files on their own
devices, and sealed blocks belonging to other members which it cannot read.
Network traffic goes to machines the member controls, and to a coordinator the
member chooses. There is no analytics, no advertising identifier, no crash
reporting.

**Privacy policy URL.** Required, even for an application that collects
nothing — Play asks for a URL, not an argument. It has to be written and
hosted; it does not exist yet.

**Foreground service justification.** `SyncService` is declared
`android:foregroundServiceType="dataSync"` and holds
`FOREGROUND_SERVICE_DATA_SYNC`. The justification is the honest one: the
application's entire purpose is keeping a folder in step with the member's own
machines, which cannot be done from a job that the system may defer for hours.
Google scrutinises `dataSync` specifically; expect to answer.

**Encryption / export compliance.** The application uses cryptography and is
open source under AGPL-3.0. That is the usual exemption, and the repository URL
is the evidence.

**Target API.** `targetSdk = 35`, which met Play's requirement when this was
written. It rises roughly yearly; a listing that stops meeting it stops
accepting updates.

## 5. Version numbers, which Play enforces

`versionCode` is an integer that **must increase on every upload**. It is `1`
in `android/app/build.gradle.kts` and has never been raised, because nothing
has ever been uploaded. Raise it before each upload; Play refuses a repeat and
the error arrives after the upload rather than before it.

`versionName` (`0.1.0`) is what a person sees and has no rule beyond being
truthful.

## 5b. Testing it without a phone, which is how the join was proved

The `x86_64` ABI in `android/app/build.gradle.kts` exists for this. There is an
AVD called `itsanas-test` on an `android-35` image.

```
D:/Android/Sdk/emulator/emulator.exe -avd itsanas-test -no-window -no-audio -no-boot-anim -gpu swiftshader_indirect
```

Then, with `D:/Android/Sdk/platform-tools` on `PATH`:

```
adb install -r android/app/build/outputs/apk/release/app-release.apk
adb shell am start -n fr.ngas.itsanas/.MainActivity
adb logcat -d | grep -iE 'FATAL|UnsatisfiedLink'
```

An `UnsatisfiedLinkError` is the failure that matters: it means the native
library did not load, which no amount of Kotlin review would have caught.

To drive the screen without looking at it, `adb shell uiautomator dump
/sdcard/ui.xml` and read the `text=` attributes. **From Git Bash, set
`MSYS_NO_PATHCONV=1` first**, or the shell rewrites `/sdcard/ui.xml` into a
Windows path and `adb pull` fails on a file name it invented.

**What this proved on 2026-09-16**, which nothing else could have: the
application installs, starts, loads the native library, opens a real node, and
**joins a coordinator**. The join was driven through the UI against a
coordinator running `--invite-only --admit-first` on the host at `10.0.2.2`,
and the proof it worked is indirect and solid — afterwards a fresh account
registering from the command line was **refused** for want of an invitation,
so the phone had consumed `--admit-first`.

It also found a defect no review had: the join succeeded and **nothing on the
phone changed**, which is indistinguishable from a button that does not work.
Somebody would tap it again. The screen now reports what happened.

## 6. What is not ready, said plainly

- **Nobody has installed the current application on a real phone.** It has run
  on the emulator, where it installs, starts, loads the native library, opens a
  node and joins a coordinator (§5b) — so the Kotlin glue and the JNI
  marshalling are no longer untested, which they were until 2026-09-16. What an
  emulator cannot show: a real radio, a real battery, Doze, and a manufacturer's
  idea of what a background service is allowed to do.
- **There is no local discovery on Android.** Two phones on one wifi do not
  find each other. They join through a coordinator, or through `addPeer` with
  an address typed in.
- **There is no privacy policy**, and Play will not take a listing without one.
- **There is no release key yet**, so every build so far is debug-signed.
